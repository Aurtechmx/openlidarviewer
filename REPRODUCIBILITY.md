# Reproducibility

This page is the single entry point for reproducing OpenLiDARViewer's build, tests, and reported analysis figures. It stitches together the pieces that also live in `README.md`, `REVIEWER_QUICKSTART.md`, and `docs/benchmarks.md`. The exact figures reported for the current release, each tied to the command that regenerates it, are in [REPRODUCIBILITY_v0.7.1-alpha.1.md](docs/releases/REPRODUCIBILITY_v0.7.1-alpha.1.md).

## Environment

- Node.js 22.18.0, the canonical toolchain, pinned in `.nvmrc`. `package.json` `engines` is deliberately wider (`^22.18.0 || >=24.11.0`) so the package installs on newer runtimes; only `.nvmrc` fixes the version the published figures come from.
- Install exactly the locked dependency set with `npm ci` (uses `package-lock.json`; do not use `npm install` for a reproducible run).

```bash
nvm use            # picks up .nvmrc (Node 22)
npm ci
```

## Commands

| Purpose | Command |
| --- | --- |
| Type check | `npm run typecheck` |
| Unit + integration tests (partitioned) | `npm run test:unit && npm run test:export && npm run test:terrain && npm run test:ui && npm run test:slow` |
| Plain build + chunk-isolation contract | `npm run test:build` |
| Production (obfuscated) build | `npm run build:live` |
| Bundle budget check | `npm run check:bundle` |
| Full release gate (all of the above + lints + plain & live smoke) | `npm run test:release` |
| Re-read the committed scientific records, and write JSON/CSV/Markdown reports | `npm run verify:scientific-records` |
| Recompute the evidence the scientific records hold, then re-read them | `npm run validate:scientific` |
| Regenerate analysis/benchmark figures | `npm run repro` |
| Package source + deploy archives | `npm run package` |

`npm run verify:scientific-records` reads what is already committed: it runs the dataset register, study, evidence-record, claim-register and freeze checks in one pass, records the commit and the tool versions it ran against, and recomputes nothing. It is the only form of this check an extracted source archive can answer. `npm run validate:scientific` runs the terrain bucket first, so the cross-implementation records under `validation/cross-implementation/pdal-pipeline/` are regenerated by the current ground filter before the study check grades them, and then runs the verifier. It takes about a minute where the verifier alone takes seconds. Neither is part of the release gate, which already sequences the same checks behind their producers.

The authoritative deterministic gate is `OLV_GATE_MODE=release npm run gate`; read the verdict from its `GATE EXIT:` line. `npm run test:release` is the static stage that gate runs first (typecheck, lints, all test buckets, both builds, bundle budget, plus plain and live-obfuscated smoke); run on its own it prints no `GATE EXIT:` line and refreshes no evidence. The broader browser matrix that a device varies, the full end-to-end suite and the mobile responsive job, runs in CI (`.github/workflows/ci.yml`), not in `test:release`. The remaining physical-device coverage gaps for a tagged release are recorded in `docs/releases/RELEASE_NOTES_v0.7.1-alpha.1.md`.

### Release gate from the source archive

The published source archive has no `.git`, so a gate run inside it cannot ask git which commit and tag it describes. Release mode takes them from the environment instead, or from the release manifest published beside the archive (`release-manifest-v<version>.json`, downloaded into the directory the archive was extracted into, or into the directory named by `OLV_RELEASE_MANIFEST_DIR`). With the manifest in place the whole reproduction is one command, run from the extracted source directory after `npm ci` and `npm run e2e:browsers`:

```bash
OLV_GATE_MODE=release npm run gate
```

Without the manifest, name the identity directly; both values are required and the commit is the full 40-character sha:

```bash
OLV_GATE_MODE=release OLV_RELEASE_COMMIT=<sha> OLV_RELEASE_TAG=v<version> npm run gate
```

The record it writes to `release/test-evidence-v<version>.json` carries `source: "archive"` and `identityFrom` (`environment`, or the manifest file name), where a run inside a checkout carries `source: "git"`. The figures are the same; the field records that the run could not confirm the identity itself. A manifest for a different version in the same directory is reported and not used.

### End-to-end browsers

`npm ci` installs the Playwright *package* but not its browsers, so a fresh
clone stops partway into `npm run test:e2e` or the full release gate. Install
them once first:

```bash
npm run e2e:browsers
```

## Determinism

- The analysis reproduction pack (`tests/reproPack.test.ts`, run via `npm run repro`) is fully deterministic: every input is generated from a fixed seed (an LCG plus Box–Muller), so the emitted metrics under `benchmarks/out/` reproduce exactly under the Node version pinned in `.nvmrc`. Another Node or V8 version can change the last digits of floating-point results. The report digest is an unkeyed SHA-256 over the report body: a match shows the digest agrees with the contents, which catches accidental edits. Anyone can recompute it after an edit, so it is not a signature and does not show who made the report. A report signed with the optional "Sign this report" key also detects a change to the report's figures or signed metadata after signing, but the signature does not show who holds the key or when it was made (see `docs/threat-model.md`).
- Test fixtures under `tests/` are synthetic and seed-generated (see `scripts/make-*.py` and `tests/fixtures/FIXTURES.md`), or explicitly licensed (see `docs/project/THIRD_PARTY_NOTICES.md`).
- Build identity is reproducible: the build honours `SOURCE_DATE_EPOCH`, and when git metadata is unavailable the commit is reported as `unknown` rather than fabricated.

## Not deterministic (by nature)

- GPU/browser **performance** figures in `docs/benchmarks.md` depend on hardware, driver, and browser, and are described there as field observations, not a formal benchmark. They are not part of the reproducible metric set above.

## Expected outputs

`npm run repro` writes `metrics.{json,md}`, the calibration file and the registration-bias file under `benchmarks/out/`. That directory is generated and git-ignored, not committed: the expected values live in the assertions of `tests/reproPack.test.ts`, which the pack checks on every run, so a clean run under the pinned Node version writes the same figures it asserts. To compare two runs, keep the first `benchmarks/out/` and diff it against the second.
