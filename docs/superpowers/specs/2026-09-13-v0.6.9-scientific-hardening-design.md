Date: 2026-09-13
Status: design, not implemented
Source: a 20-item audit run against v0.6.8 (tag a61fccd1, commit 7024aeba). Every
item below was verified against source; items the audit raised that the code had
already answered are listed under "Already correct" so nobody re-opens them.

## 1. Export authorization is not monotone

A scan that is blocked for insufficient coordinate precision becomes an
authorized exploratory export when its CRS is removed.

- `inMemoryPrecision.ts:354` — losing the unit nulls the metre figure.
- `inMemoryPrecision.ts:436` — `step === undefined || step <= budget` returns the
  same `{ ok: true }`, so "not measured" and "within budget" are one verdict.
- `exportManifest.ts:149` — the resolver refuses only `precision !== null && !ok`.
- `contourStudioLaunchState.ts:166` — unknown units are an exploratory reason,
  not `unavailable`.

A 400 km scan with a metre CRS writes nothing; the same scan without the CRS
writes a deliverable carrying coordinates the Float32 buffer cannot distinguish.

Fix: make the precision gate three-valued (`ok` / `refused` / `unmeasured`) and
have `resolveExportDecision` treat `unmeasured` as blocking for a metric
deliverable. Keep the cartographic path open, since it makes no metric claim.

Tests: the production permit under COMBINED degradation. `tests/contourExport
Permit.test.ts` passes `precision: null` in every unit-downgrade case, so this
interaction is currently unexercised. `tests/authorizationMonotonicity.test.ts`
covers `ProcessService.authorize`, which no product uses
(`ProductExecutorRegistry` is itself unreachable) — it must also cover
`resolveExportDecision`.

## 2. Registration acceptance scales with the scene

`main.ts:5392` sets `maxResidualM = span * 0.1`, where `span` is the larger XY
extent. 50 m pair accepts 5 m; 2 km tile accepts 200 m. The same constant is the
inlier radius (`icpRegister.ts:279`), so `inlierFraction` counts anything within
200 m as an inlier and the `< 0.5` low-overlap withholding gate
(`alignEpochs.ts:390`) becomes unreachable on large scenes. One constant defeats
two guards.

Fix: derive the gate from DTM cell size / estimated point spacing / requested
LoD, not from extent. Fail closed with a reason code — the vocabulary already
exists at `registrationModel.ts:45-46, 59-81` and is unused by this path.

Tests: identical physical misregistration embedded in scenes of very different
extent must reach the same verdict.

## 3. Registration can chase the signal it measures

Correspondences are chosen by full 3-D distance including `dz`
(`icpRegister.ts:152`), and those pairs drive the yaw and XY centroid closure
(`:243-255`). Trimming exists but production never enables it — `main.ts:5394`
passes no `trimFraction`, so the shipped fit is plain least squares over every
sampled point, vegetation and changed ground included
(`epochFramePrep.ts:129-130` feeds raw positions). A uniform vertical change is
absorbed by the warm start; a localised one is not.

The applied transform is correctly `yaw+xy` with Z zeroed
(`alignEpochs.ts:425-427`) — the defect is that Z participates in the solve that
produces the horizontal answer.

Fix: match correspondences in XY, or restrict the fit to explicitly stable
terrain.

Tests: large vertical change with zero horizontal shift; known XY shift with no
vertical change; both together; unstable region dominating part of the scene.

## 4. A 3-D fit residual is used as a vertical sigma

`icpRegister.ts:289` computes a 3-D RMS; it becomes `rmsResidualM`
(`alignEpochs.ts:361`), then `registrationSigmaM` (`main.ts:5410`), then the
systematic term of the volume uncertainty (`changeUncertainty.ts:222`). The code
already names this a proxy in prose (`compareDtms.ts:437-441`). Horizontal
residual, vertical residual on stable surfaces, vertical bias and robust spread
are not computed at all.

Fix: report vertical registration uncertainty as unknown rather than
substituting the wrong statistic, until a stable-surface vertical residual
exists. If it is reported, it must be the vertical residual, with bias and NMAD
beside it.

## 5. One stray point coarsens a whole comparison

`compareEpochs.ts:154` — `cellSizeM = max(0.25, extent/256)` over the raw union
bbox (`:104-124`), no robust bound, despike happens after the grid is fixed. A
point 5 km out gives 19.5 m cells for both epochs. Re-cropping the same pile
changes the estimator while the local data are unchanged.

Fix: derive the cell size from ground-return spacing with a robust extent
bound. Report the selected size and the reason; today it reaches only the `.asc`
header (`changeRaster.ts:47`) and never the panel.

## 6. Change detection discards trusted class 2

`EpochCloud` (`compareEpochs.ts:29-68`) carries positions, CRS, datum and both
unit factors — and no classification and no provenance. The field is dropped at
the `EpochFrameInput` boundary (`epochFramePrep.ts:31-38`) and again at the
rebuild (`:130-131`), then SMRF runs unconditionally on both epochs
(`compareEpochs.ts:201`). The single-scan path has a full trusted-ground
implementation (`analyseContours.ts:740-752`, `classificationFilter.ts:40`);
none of it reaches change detection. No test covers epoch classification.

Fix: carry classification and a ground-basis record per epoch; use authoritative
class 2 when present; record which basis each epoch used; refuse or warn when the
two bases differ. This is a method change for the change products — new method
id, validation re-run, regenerated metrics.

## 7. Derived ground can be trusted as authoritative

`deriveClassification.ts:54` emits `DERIVED_GROUND = 2`. The AUTO-trust test is
`class2Count === keptCandidateCount` (`analyseContours.ts:752`), which OLV's own
heuristic labels satisfy. SMRF is then skipped and the despike disabled
(`:954`, `:1008`) and the run reports "Trusted N ASPRS class 2 (ground) point(s)"
for ground no surveyor classified. `groundIsDerived` is computed
(`Viewer.ts:2377`) and threaded to Contour Studio (`terrainAnalysisRunner.ts:668`)
but never into `computeTerrainCore`.

Fix: thread `groundIsDerived` into the terrain core and exclude derived labels
from AUTO trust. Explicit trust of derived ground may remain, named as such.

## 8. Labels that overstate — wording only

- `exportProvenance.ts:698` stamps `olv.ground.smrf` on every terrain export,
  including trusted-class-2 runs where SMRF provably never ran (`:954`).
- `README.md:161` says every export routes through one evidence gate; measurement
  CSV/GeoJSON, the measurement reports and the map sheet call `evidenceStatus`
  directly (`measurementExport.ts:356`, `measurementReport.ts:195`,
  `mapSheetPdf.ts:73`) with no launch, precision or composition term.
- `METHOD_REGISTRY.md:3` calls the registry the catalogue of methods the viewer
  "runs" while listing three it does not, and
  `olv.contour.generalize.terrain-adaptive` is stamped into real exports
  (`contourExportIntent.ts:139-142`) while its registered implementation is
  unreachable — the running pass is `terrainAwareTolerance.ts:45`.
- `METHOD_VERSIONS.md:11` and `RELEASE_NOTES_v0.6.6.md:107` contradict each other
  about which id a generalized export carries. The code sides with the notes.
- The DTM claim publishes "min-return gridding" (`claim-register.yaml:472,476`,
  and `docs-site/validation/claim-register.generated.md:22`) while the delivered
  surface is median (`liveDtmConstants.ts:24`). The register's `scope.unsupported`
  never says the shipped estimator differs from the validated one.

## 9. Register and registry gaps

- Seven claims carry no `methodId`: DSM, CHM, HILLSHADE, QUALITY-LEVEL,
  CHANGE-RASTER, CHANGE-VOLUME, UNCERTAINTY-BAND. CHANGE-VOLUME names its method
  in prose (`claim-register.yaml:1013`) where a field would be machine-checked.
- Two shipping methods have no claim at all: `olv.class.derived-heuristic`
  (`methodRegistry.ts:81`, with a corpus evaluation) and
  `olv.validation.spatial-block` (`methodRegistry.ts:162`, shipping in panel and
  PDF).
- HOLDOUT-RMSE calls blocked CV "pending" (`claim-register.yaml:806,814`) while
  it ships (`analyseContours.ts:1127`).
- `unreachable-modules.json:22` records 60 unreachable modules; the file lists 38.
- `methodRegistry.ts` has one DTM entry whose summary never mentions aggregation,
  so median/mean/min move no id and no version.

## 10. Smaller, bounded

- The independence caveat is computed (`changeUncertainty.ts:273-275`) and never
  rendered — `summarizeChange` never reads `u.caveats`, and `changeFinding`
  (`sessionFindings.ts:110`) has no call site.
- Grid recommendation uses total analysed returns (`recommendGrid.ts:82`,
  `analyseContours.ts:1497`) while `gf.groundPointCount` sits unused beside it;
  the same field means different populations on the SMRF and trusted paths.
- `analysisFreshness.ts:55` compares `targetId`, `classificationEpoch` and
  `crsRevision`; `coverageMode` is written and never read, so a coverage drop
  does not invalidate a result.
- Hold-out sample count `n` is in the panel (`verticalAccuracy.ts:87`) and absent
  from the terrain report PDF and export provenance.
- `DEFAULT_LOD_M = 0.1` (`changeDetection.ts:132`) is the entire random error
  budget (`changeUncertainty.ts:162-164, 220`) and no UI can override it, so
  `levelOfDetectionSupplied` is unreachable.
- Held-out XY set the grid extent and origin in both hold-out paths
  (`holdoutRmse.ts:332-348`, `analyseContours.ts:1124-1126`) — a transductive
  dependency that is nowhere disclosed.
- Reliability tolerance tau is the RMSE of the same sample being scored
  (`analyseContours.ts:1160-1162`); the curve is cross-fit but tau is not
  (`calibrateConfidence.ts:247`), and the calibrated mean reaches the readiness
  gate (`dtmQualityGate.ts:181`).

## Excluded from v0.6.9

Changing the default ground filter (`groundFilter.ts:328` uses `cut-surface`,
not the published SMRF `object-mask` rule), the DTM aggregation, or the DSM
estimator (`buildDsm.ts:69`, raw max, outlier-sensitive). Each is a method
change requiring a new id, a full validation re-run and regenerated frozen
metrics. They are releases of their own, not hardening.
