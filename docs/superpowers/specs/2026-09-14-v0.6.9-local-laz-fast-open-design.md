# v0.6.9 local LAZ open: verified roadmap

Date: 2026-09-14
Status: roadmap; A, D and E implemented, B measured in Node and the browser, C and F sequenced on the measurement
Source: an external 83-section prompt on local LAS/LAZ open time. Its
description of the current pipeline was checked step by step against the tree
before any of it was accepted. Corrections and the resulting order of work are
recorded here.

## The pipeline as it is

The prompt's account of an ordinary (non-COPC, non-heavy) local LAZ open is
accurate in every step. Verified:

1. `openScan.ts:251` awaits the Viewer, then `:254` reads 4,096 bytes and
   runs `detectCopc`.
2. `openLocalHeavyLas.ts:113` reads `min(size, 65,536)` bytes through a
   `LocalFileRangeSource`, parses the LAS header (`:127`) and runs `planLoad`
   (`:196`). An ordinary file returns `not-heavy` at `:205`.
3. `loadFile.ts:246` reads 16,384 bytes, sniffs the format, parses the header
   and runs `planLoad` a second time (`:265`, `:117-134`).
4. `loadFile.ts:572` reads the whole file into one `ArrayBuffer`
   (`readWholeFileAbortable`, `:506-522`) and transfers it to the parse
   worker (`:666-669`).
5. For LAZ, `loadLas.ts:186` tries `decodeLazPooled`, which engages only at
   `PARALLEL_DECODE_MIN_POINTS = 10,000,000` declared records
   (`lazChunkWorkerClient.ts:144`); otherwise `decodeLaz`.
6. `decodeLaz` copies the entire compressed file a second time, into the
   laz-perf heap: `lazDecode.ts:117` mallocs `byteLength`, `:121`
   `HEAPU8.set(fileBytes, filePtr)`. Below ten million points the worker
   therefore holds the compressed file twice plus the decoded output.
7. Nothing renders before the final cloud. `buildPreviewSample` and
   `PreviewCloudSource` have one caller, `heavyLasExecutor.ts:491-501`. The
   first `viewer.addCloud` on this path is `openScan.ts:414`, after the
   worker resolves.

Three head reads, all from offset 0, total 86 KiB, issued sequentially on
the main thread, with the header parsed and the plan built twice.

## Corrections to the source prompt

- §2 lists twelve components as reusable. All twelve exist. Five are reachable
  from the ordinary path only when the pool engages (`readLazChunkTable`,
  `lazChunkWorker`, `LazChunkWorkerClient`, `DecodeWorkerPool`,
  `decodeLazChunkLocal`, `decodeLazParallel`, `stratifiedSampleIndices`);
  four are reachable only from the heavy/OOC path (`previewSampler`,
  `PreviewCloudSource`, `chunkedLazSource`, `openSlicedLasSource`);
  `LocalFileRangeSource` is used by the ordinary path for the 64 KiB peek.
  "Bring the right subset to ordinary opens" is the correct framing; nothing
  needs inventing.
- §18 understates the copy. The prompt describes the double copy as a
  legacy-path detail. It is the common case: every LAZ under ten million
  declared points takes it.
- §33 "first visible frame must be measured, not inferred": `firstRenderMs`
  (`openScan.ts:471`) already measures framing plus the first render pass
  after `addCloud`, and `LoadTelemetry` records sniff, file read, transfer,
  parse, decode, downsample, GPU upload and total. What is absent is a
  preview commit time, because there is no preview.
- §51 "build a local-LAZ benchmark harness": `tests/benchmark/lazDecodeBaseline.test.ts`
  measures single-reader decode throughput on a PDAL-compressed ladder, gated
  on `LAZ_DECODE_BENCH=1`. It measures decode, not open: no file read, no
  worker transfer, no GPU commit, no first-frame time. It is the baseline leg
  for item C, not for TTFP.
- The prompt's §3 gate (TTFP at least 50% faster, TTR within 5%, staging
  memory 35% lower) is a promotion criterion for items C to E. Item A cannot
  meet it and does not claim to. E meets the TTFP half from 2 M points up
  and leaves TTR unchanged; the memory half is C's.
- Not in the prompt, found by B's browser half: the pool's URL switches
  (`?decodePool=on`, `?decodePool=off`, `?decodeWorkers=N`) never reached the
  whole-file LAZ decode. That decode runs inside the parse worker, and the
  flags were read there from `window.location`, which a worker does not have,
  so every session saw the defaults: the pool engaged at ten million points
  and could be neither requested below it nor refused above it. The parse
  request now carries the page's query and the worker primes its flags from
  it (`primeDevFlags`). No default changed.

## The order of work

Each item is gated on the one before it. A is non-numerical and landed.
B's numbers reordered what follows: D and E move time, C moves memory. D
landed on B's browser measurement. None of C, E or F may be promoted without
B's before/after on the pinned fixtures.

### A. One head read (implemented)

`openScan` reads the first `min(size, 64 KiB)` once and hands the bytes to
both consumers: `openLocalHeavyLas` through `env.head`, `loadFile` through
`LoadOptions.head`. `detectCopc` needs 589 bytes, the heavy peek 64 KiB and
`preflightFile` 16 KiB, so the one read covers all three. A caller that
supplies no head gets the reads it had before; the generic loader does not
depend on `openScan`. This removes two of three reads and one of two header
parses. It does not change what is decoded, the sample, the point order or any
number in any output.

Not claimed: a measurable TTFP gain. Three sub-100 KiB slices of a local file
cost single milliseconds; the whole-file read that follows is the cost.

### B. Baseline, measured (Node half implemented; browser half open)

`tests/benchmark/localOpenBaseline.test.ts` (`npm run benchmark:local-open`)
times the three phases of an open separately over the PDAL-compressed ladder
`lazDecodeBaseline` builds: the one prefix read item A leaves, the whole-file
read, and the single-reader decode every file under the pool threshold takes.
Best of three, every run printed. Node has `File` but no Worker, so it cannot
engage the pool and has no frame; it measures TTR up to decoded points.

Measured 2026-09-14, 14 cores, Node 22.23.2, files in page cache:

| points | LAZ | prefix read | whole-file read | decode | TTR |
|---:|---:|---:|---:|---:|---:|
| 1 M | 2.0 MB | 0.1 ms | 0 ms | 329 ms | 330 ms |
| 5 M | 9.9 MB | 0.1 ms | 1 ms | 1,563 ms | 1,563 ms |
| 10 M | 19.7 MB | 0.1 ms | 1 to 3 ms | 3,118 ms | 3,119 ms |

What this settles:

- Decode is the open. The single reader runs at 3.2 M points/s and is
  99.9 % of TTR on every rung. The whole-file read the prompt centres on
  costs single milliseconds here; item A's saving is real and unmeasurable.
- The prompt's ordering is therefore inverted for time. Range reads (C)
  change memory, not TTR: they remove the resident compressed file and the
  laz-perf heap copy, which is 2 × the LAZ size. Routing more files to the
  pool (D) and decoding a preview subset first (E) are the two levers on
  time, and D is the cheaper one: at 10 M points the pool engages today and
  fourteen cores are available, while a 5 M file spends 1.5 s in one reader.
- These are page-cache reads of synthetic files at 2 bytes per point. A
  field tile is 10 to 15 bytes per point and comes off disk; the read phase
  grows, but a 47 M-point tile still spends about 15 s in a single reader
  against a read in the hundreds of milliseconds. The conclusion holds.

The pooled decoder on the same ladder (`tests/benchmark/localOpenPooled.test.ts`,
`npm run benchmark:local-open-pooled`), measured 2026-09-14: the real
`lazChunkWorker` module bundled for Node and run in `worker_threads` behind
the pool's `workerFactory` seam, four workers (the policy's hard cap), best of
three. Cold builds and disposes a pool per decode, which is what
`decodeLazPooled` does for every file; warm reuses one. Each rung's pooled
output was checked byte-identical to the single reader's before it was timed.

| points | chunks | chunk table | single reader | pooled cold | pooled warm | fixed cost | cold speed-up |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.25 M | 5 | 1 ms | 119 ms | 101 ms | 53 ms | 48 ms | 1.2 × |
| 0.5 M | 10 | 0 ms | 232 ms | 138 ms | 84 ms | 54 ms | 1.7 × |
| 1 M | 20 | 0 ms | 468 ms | 196 ms | 139 ms | 57 ms | 2.4 × |
| 2 M | 40 | 1 ms | 929 ms | 331 ms | 277 ms | 54 ms | 2.8 × |
| 5 M | 100 | 0 ms | 2,344 ms | 749 ms | 692 ms | 58 ms | 3.1 × |
| 10 M | 200 | 1 ms | 4,835 ms | 1,421 ms | 1,366 ms | 54 ms | 3.4 × |

The single-reader column is slower than in the first table because the
machine was slower when this ran: the first benchmark, re-run in the same
state, gave 483 ms and 4,650 ms at 1 M and 10 M. Ratios within one run are
the result; absolute times do not compare across the two tables.

What this adds:

- The chunk table costs about a millisecond to read from the file by range at
  every size: one prefix read and one read at the table offset. C's read side
  is free; its decode side is the work.
- The pool's fixed cost in threads is about 55 ms for four workers: four
  laz-perf instantiations plus thread start. It is repaid by 250 k points, and
  the pooled path beats the single reader at every rung measured. Four workers
  reach 3.4 × at 10 M, where 200 chunks keep every lane busy.
- Threads bound the browser from below. A browser module worker also fetches
  and compiles the worker script and its embedded WASM on each start, the cost
  the constant's comment puts at a couple of hundred milliseconds for four.
  Paid in full on top of the thread figures, the crossover sits near 1 M
  points. It does not sit at 10 M.

The browser, measured 2026-09-14 (`tests/e2e/localOpenDevice.spec.ts`,
`npm run benchmark:local-open-device`): headless Chromium on the same
machine, each open on a fresh page through the file input, `?decodePool=off`
against `?decodePool=on`, three opens per mode. The decode time is the load
telemetry's own row; the chunk workers are counted from the page's worker
events, four on every pooled open and none on a single one.

| points | single decode, first / best | pooled decode, first / best | speed-up (best) |
|---:|---:|---:|---:|
| 1 M | 466 / 433 ms | 198 / 183 ms | 2.4 × |
| 2 M | 841 / 841 ms | 315 / 314 ms | 2.7 × |
| 5 M | 2,057 / 2,056 ms | 705 / 705 ms | 2.9 × |
| 10 M | 3,963 / 3,912 ms | 1,246 / 1,246 ms | 3.1 × |

Module Workers cost what threads cost here: the first pooled open of each
rung, the one that also fetches the worker script, is within 15 ms of the
best. The wall-clock row is left out because headless Chromium's software GPU
adds two to three seconds of upload above 5 M points that a real device does
not pay; the decode row is the like-for-like column.

Still to measure: rungs below 1 M in the browser, and for E the first-frame
and preview-commit times (§33).

### C. Chunk table from the file, range-based pooled decode (§8, §15 to §20)

`readLazChunkTable` already reads the table through a `RangeSource`; today it
is handed an `ArrayBufferRangeSource` over the already-whole buffer
(`decodeLazChunked.ts:270`). Feeding it the `LocalFileRangeSource` instead,
and having `decodeLazParallel` read each chunk's byte range on demand rather
than slicing a resident buffer, removes the whole-file `ArrayBuffer` from the
pooled path. The output contract is unchanged: `decodeLazParallel` already
places chunk results into one preallocated output in file order
(`:347-385`), so the sample and order are what `decodeLaz` produces. Gate:
byte-identical `RawPoints` against the current path on every fixture, then
B's TTR and staging-memory comparison.

### D. Routing by measurement (§7, §21, §25) (implemented)

`PARALLEL_DECODE_MIN_POINTS` was ten million. The pool already existed and
already produced the same points as the single reader; what was unknown was
the size at which its fixed cost (worker spin-up, laz-perf init per worker,
chunk-table read) is repaid. B measured it: in threads the pool wins from
250 k points, and in the browser, with real module Workers and their script
fetch paid, it wins by 2.4 × at 1 M, the smallest rung the browser leg ran.
The constant is now one million. Files below it stay on the single reader,
where the thread leg shows the gain shrinking to 1.2 × at 250 k and the
browser has not measured at all. D did not need C: it changed one constant on
a path that ships today, and the pooled output is checked byte-identical to
the single reader's on every rung of the Node leg.

### E. Preview before the final cloud (§11 to §14, §34 to §36, §48) (implemented)

The pooled decoder now decodes every sixteenth chunk first and hands a copy of
those records to the caller before the rest of the file is decoded
(`decodeLazParallel`, `onPreview`). The parse worker posts that subset as a
`preview` reply; the loader hands it to `openScan`, which hides the empty
state, shows it through `Viewer.showPreviewCloud` and fits the camera to it
once. When the final cloud arrives the commit adds it and removes the
stand-in in the same task, and skips its own framing, so the pose does not
move twice. A failed or cancelled load takes the stand-in down and puts the
empty state back. The stand-in is not a layer: nothing lists, measures,
analyses or exports it, and a preview that lands after Cancel is dropped.

Identity gate: the final output is assembled exactly as before; only the
order the chunks decode in changes, and `tests/decodeLazChunked.test.ts`
checks the assembled buffer against the single reader and the preview's
records against the same chunks of that buffer. Single-chunk files and the
single reader send no preview.

Measured 2026-09-15 in the browser leg (`npm run benchmark:local-open-device`,
headless Chromium on the deterministic lane, pool at the policy's four
workers, fresh page per open, best of three; the run was cut off before its
10 M rung):

| points | single decode | pooled decode | preview arrives | wall to final, single / pooled |
|---:|---:|---:|---:|---:|
| 1 M | 437 ms | 188 ms | 183 ms | 536 / 1,120 ms |
| 2 M | 852 ms | 305 ms | 226 ms | 973 / 1,333 ms |
| 5 M | 2,038 ms | 700 ms | 303 ms | 4,055 / 2,587 ms |

The 10 M rung, by hand in Chromium with WebGPU: preview at 285 ms, pooled
decode 1,330 ms, and the whole open 41.5 s against 64.2 s with the pool off.
The difference between decode and wall on that file is a 40 s voxel
downsample of the 5 M-point display sample, which runs the same way on both
paths and is not part of this roadmap.

What the numbers say:

- The preview arrives at a fixed cost of 180 to 300 ms whatever the size:
  worker start plus the first chunk of each lane. Everything the user waits
  for beyond that now happens behind a cloud that is already on screen.
- The first visible frame is the preview's first render, which pays the
  point pipeline's compile. That compile was always paid; it moves from
  after the final decode to before it. The load telemetry does not time it,
  and the wall column shows it: at 1 M and 2 M the pooled wall grows by the
  compile the single path pays after `done`, not by any added work. Time to
  the final cloud on screen is unchanged at those sizes and shorter at 5 M.
- At 1 M the preview and the final arrive within a few milliseconds of each
  other, so the gain there is nil; from 2 M up it is the decode time.

### F. The second copy (§18)

`decodeLaz` copies the file into the laz-perf heap because the legacy
`LASZip.open(ptr, len)` reads from WASM memory. Removing the copy needs a
streaming reader or the pooled path. Once D routes more files to the pool,
the copy applies to fewer files; it is not fixed by editing `lazDecode.ts`.

## Not in scope

§24 embedded-base64 laz-perf startup, §27 OPFS for ordinary opens (the
prompt itself forbids it), §81 the Rust seam, §37 preview-only appearance
defaults. Nothing that changes a sample, a stride, a point order or a
provenance field ships under this roadmap without C's identity gate.
