# v0.6.9 local LAZ open: verified roadmap

Date: 2026-09-14
Status: roadmap; A implemented, B measured (Node half), C to F sequenced on the measurement
Source: an external 83-section prompt on local LAS/LAZ open time. Its
description of the current pipeline was checked step by step against the tree
before any of it was accepted. Corrections and the resulting order of work are
recorded here.

## The pipeline as it is

The prompt's account of an ordinary (non-COPC, non-heavy) local LAZ open is
accurate in every step. Verified:

1. `openScan.ts:251` awaits the Viewer, then `:254` reads 4,096 bytes and
   runs `detectCopc`.
2. `openLocalHeavyLas.ts:113` reads `min(size, 65,536)` bytes through a
   `LocalFileRangeSource`, parses the LAS header (`:127`) and runs `planLoad`
   (`:196`). An ordinary file returns `not-heavy` at `:205`.
3. `loadFile.ts:246` reads 16,384 bytes, sniffs the format, parses the header
   and runs `planLoad` a second time (`:265`, `:117-134`).
4. `loadFile.ts:572` reads the whole file into one `ArrayBuffer`
   (`readWholeFileAbortable`, `:506-522`) and transfers it to the parse
   worker (`:666-669`).
5. For LAZ, `loadLas.ts:186` tries `decodeLazPooled`, which engages only at
   `PARALLEL_DECODE_MIN_POINTS = 10,000,000` declared records
   (`lazChunkWorkerClient.ts:144`); otherwise `decodeLaz`.
6. `decodeLaz` copies the entire compressed file a second time, into the
   laz-perf heap: `lazDecode.ts:117` mallocs `byteLength`, `:121`
   `HEAPU8.set(fileBytes, filePtr)`. Below ten million points the worker
   therefore holds the compressed file twice plus the decoded output.
7. Nothing renders before the final cloud. `buildPreviewSample` and
   `PreviewCloudSource` have one caller, `heavyLasExecutor.ts:491-501`. The
   first `viewer.addCloud` on this path is `openScan.ts:414`, after the
   worker resolves.

Three head reads, all from offset 0, total 86 KiB, issued sequentially on
the main thread, with the header parsed and the plan built twice.

## Corrections to the source prompt

- §2 lists twelve components as reusable. All twelve exist. Five are reachable
  from the ordinary path only when the pool engages (`readLazChunkTable`,
  `lazChunkWorker`, `LazChunkWorkerClient`, `DecodeWorkerPool`,
  `decodeLazChunkLocal`, `decodeLazParallel`, `stratifiedSampleIndices`);
  four are reachable only from the heavy/OOC path (`previewSampler`,
  `PreviewCloudSource`, `chunkedLazSource`, `openSlicedLasSource`);
  `LocalFileRangeSource` is used by the ordinary path for the 64 KiB peek.
  "Bring the right subset to ordinary opens" is the correct framing; nothing
  needs inventing.
- §18 understates the copy. The prompt describes the double copy as a
  legacy-path detail. It is the common case: every LAZ under ten million
  declared points takes it.
- §33 "first visible frame must be measured, not inferred": `firstRenderMs`
  (`openScan.ts:471`) already measures framing plus the first render pass
  after `addCloud`, and `LoadTelemetry` records sniff, file read, transfer,
  parse, decode, downsample, GPU upload and total. What is absent is a
  preview commit time, because there is no preview.
- §51 "build a local-LAZ benchmark harness": `tests/benchmark/lazDecodeBaseline.test.ts`
  measures single-reader decode throughput on a PDAL-compressed ladder, gated
  on `LAZ_DECODE_BENCH=1`. It measures decode, not open: no file read, no
  worker transfer, no GPU commit, no first-frame time. It is the baseline leg
  for item C, not for TTFP.
- The prompt's §3 gate (TTFP at least 50% faster, TTR within 5%, staging
  memory 35% lower) is a promotion criterion for items C to E. Item A cannot
  meet it and does not claim to.

## The order of work

Each item is gated on the one before it. A is non-numerical and landed.
B's Node half produced the numbers below and reordered what follows: D and E
move time, C moves memory. None may be promoted without B's before/after on
the pinned fixtures.

### A. One head read (implemented)

`openScan` reads the first `min(size, 64 KiB)` once and hands the bytes to
both consumers: `openLocalHeavyLas` through `env.head`, `loadFile` through
`LoadOptions.head`. `detectCopc` needs 589 bytes, the heavy peek 64 KiB and
`preflightFile` 16 KiB, so the one read covers all three. A caller that
supplies no head gets the reads it had before; the generic loader does not
depend on `openScan`. This removes two of three reads and one of two header
parses. It does not change what is decoded, the sample, the point order or any
number in any output.

Not claimed: a measurable TTFP gain. Three sub-100 KiB slices of a local file
cost single milliseconds; the whole-file read that follows is the cost.

### B. Baseline, measured (Node half implemented; browser half open)

`tests/benchmark/localOpenBaseline.test.ts` (`npm run benchmark:local-open`)
times the three phases of an open separately over the PDAL-compressed ladder
`lazDecodeBaseline` builds: the one prefix read item A leaves, the whole-file
read, and the single-reader decode every file under the pool threshold takes.
Best of three, every run printed. Node has `File` but no Worker, so it cannot
engage the pool and has no frame; it measures TTR up to decoded points.

Measured 2026-09-14, 14 cores, Node 22.23.2, files in page cache:

| points | LAZ | prefix read | whole-file read | decode | TTR |
|---:|---:|---:|---:|---:|---:|
| 1 M | 2.0 MB | 0.1 ms | 0 ms | 329 ms | 330 ms |
| 5 M | 9.9 MB | 0.1 ms | 1 ms | 1,563 ms | 1,563 ms |
| 10 M | 19.7 MB | 0.1 ms | 1 to 3 ms | 3,118 ms | 3,119 ms |

What this settles:

- Decode is the open. The single reader runs at 3.2 M points/s and is
  99.9 % of TTR on every rung. The whole-file read the prompt centres on
  costs single milliseconds here; item A's saving is real and unmeasurable.
- The prompt's ordering is therefore inverted for time. Range reads (C)
  change memory, not TTR: they remove the resident compressed file and the
  laz-perf heap copy, which is 2 × the LAZ size. Routing more files to the
  pool (D) and decoding a preview subset first (E) are the two levers on
  time, and D is the cheaper one: at 10 M points the pool engages today and
  fourteen cores are available, while a 5 M file spends 1.5 s in one reader.
- These are page-cache reads of synthetic files at 2 bytes per point. A
  field tile is 10 to 15 bytes per point and comes off disk; the read phase
  grows, but a 47 M-point tile still spends about 15 s in a single reader
  against a read in the hundreds of milliseconds. The conclusion holds.

Still to measure before D and E are promoted: the pooled decoder on the same
ladder with real workers (Node `worker_threads` behind the pool's
`workerFactory` seam, or the browser), its spin-up and chunk-table costs, and
in the browser the first-frame and preview-commit times (§33).

### C. Chunk table from the file, range-based pooled decode (§8, §15 to §20)

`readLazChunkTable` already reads the table through a `RangeSource`; today it
is handed an `ArrayBufferRangeSource` over the already-whole buffer
(`decodeLazChunked.ts:270`). Feeding it the `LocalFileRangeSource` instead,
and having `decodeLazParallel` read each chunk's byte range on demand rather
than slicing a resident buffer, removes the whole-file `ArrayBuffer` from the
pooled path. The output contract is unchanged: `decodeLazParallel` already
places chunk results into one preallocated output in file order
(`:347-385`), so the sample and order are what `decodeLaz` produces. Gate:
byte-identical `RawPoints` against the current path on every fixture, then
B's TTR and staging-memory comparison.

### D. Routing by measurement (§7, §21, §25)

`PARALLEL_DECODE_MIN_POINTS` is ten million. With C in place the pool's
fixed cost changes, and the threshold is a number B can set: the point at
which the pooled path's TTR beats the single reader on the pinned hardware.
Tiny files stay on the simple path. The threshold is not lowered on
reasoning.

### E. Preview before the final cloud (§11 to §14, §34 to §36, §48)

`buildPreviewSample` and `PreviewCloudSource` exist and are tested on the
heavy path. Attaching a stratified preview from C's chunk ranges, framing
from the header, and replacing it atomically at final commit is the change
that moves TTFP. It is last because it depends on C for its reads and on B to
show the gain and to catch a double camera jump. The preview is honest by
construction only if the final sample is unchanged, which is C's gate.

### F. The second copy (§18)

`decodeLaz` copies the file into the laz-perf heap because the legacy
`LASZip.open(ptr, len)` reads from WASM memory. Removing the copy needs a
streaming reader or the pooled path. Once D routes more files to the pool,
the copy applies to fewer files; it is not fixed by editing `lazDecode.ts`.

## Not in scope

§24 embedded-base64 laz-perf startup, §27 OPFS for ordinary opens (the
prompt itself forbids it), §81 the Rust seam, §37 preview-only appearance
defaults. Nothing that changes a sample, a stride, a point order or a
provenance field ships under this roadmap without C's identity gate.
